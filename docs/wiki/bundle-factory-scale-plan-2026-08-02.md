> Владелец сформулировал цель 2026-08-02, после того как ручная публикация
> заработала от одной кнопки. Документ описывает, что нужно построить, в каком
> порядке, и какие места нельзя ускорять без потери гарантий.

## 1. Чего хочет владелец (его словами, без интерпретации)

> «Я планирую создавать листинги сотнями. Не планирую в каждый листинг заходить
> и отдельно нажимать паблиш. Даю ТЗ создать 200 листингов, через несколько
> часов возвращаюсь, вижу что все 200 созданы, несколько проверяю, потом выделяю
> всю партию и нажимаю один раз опубликовать. Потом могу попросить 1000, из них
> проверю штук 10, и сразу опубликовать 1000.
>
> Вообще должно работать так, что я поставлю крон-задачу: каждый час будет
> создаваться по 5–10 листингов, и нон-стопом идёт неделю, месяц.»

Три отдельные способности:

- **A. Партия сборки** — одно ТЗ → сотни черновиков, без присмотра.
- **B. Пакетная публикация** — выделил партию → одно нажатие → всё уехало.
- **C. Непрерывная фабрика** — расписание, которое само подбирает, что строить.

## 2. Что уже есть (проверено 2026-08-02)

| Способность | Состояние |
|---|---|
| Сборка N листингов из одного промпта | **Есть.** `GenerationJob` + `GenerationWorkItem`, тик через `/api/cron/bundle-factory-tick`, три попытки на позицию, перезапуск упавших кнопкой |
| Промоушен → валидация → фид | **Есть, проверено до `ok: true`** на живой схеме Walmart |
| Публикация одного листинга | **Есть,** от одной кнопки: promote → validate → approve → feed POST |
| Опрос статуса до LIVE | **Есть,** `/api/cron/bundle-factory-poll-pending` + проверка витрины покупателя |
| Остатки 50 на все склады при выходе в LIVE | **Есть** |
| Партия из списка черновиков | **Нет.** Кнопка публикации только построчная |
| Расписание непрерывной сборки | **Нет** |

Ограничения, которые важны для дизайна:

- Фид `MP_ITEM` принимает **массив** `MPItem[]` (подтверждено живой схемой:
  обязательные пути вида `$.MPItem[*].Orderable.sku`). Сейчас мы кладём в фид
  **ровно один** товар.
- `runDistribution` уже ходит партиями (`batchSize`, по умолчанию 5) и делает
  паузу секунду между партиями — но каждая позиция = отдельный фид.
- Пул UPC: 13 037 свободных. При 10 листингах в час это ~54 дня непрерывной
  работы. Нужен сигнал на нижнем пороге, а не сюрприз.

## 3. Что нельзя ускорять

Эти правила куплены инцидентами (AGENTS.md §7) и остаются в силе на любом масштабе:

1. **Один SKU — один POST, ноль повторов.** Неизвестный результат POST-а
   выясняется только чтением. В коде это уже обеспечено
   `MarketplaceSubmissionAttempt` с уникальным `active_key = sku.id`; пакетная
   очередь обязана ходить через тот же забор, а не мимо него.
2. **Публикация — решение владельца.** Массовая публикация не отменяет этого:
   она превращается в *одно* решение на партию с явным потолком, а не в
   отсутствие решения.
3. **Проверка витрины покупателя после записи.** «Фид принят» ≠ покупатель
   видит правильный товар.
4. **Контент только с точного варианта.** На тысяче листингов это единственная
   защита от повторения когорты 220.

## 4. План

### Этап A — партия в интерфейсе (самое дешёвое, даёт сразу многое)

- Чекбоксы в списке черновиков, «выделить все отфильтрованные».
- Фильтры: канал, статус валидации, партия сборки (`generation_job_id`), дата.
- Кнопка **Publish selected (N)** с одним подтверждением на партию.
- Публикация уходит **в очередь**, а не в HTTP-запрос: 200 листингов в одном
  запросе — гарантированный таймаут.

**Модель очереди.** Не изобретать: у сборки уже есть `GenerationJob` +
`GenerationWorkItem` с попытками, локом и тиком. Публикация получает такую же
пару (`PublishBatch` + `PublishBatchItem`) либо переиспользует ту же, с другим
`current_stage`. Прогресс рисуется тем же компонентом, что и сборка.

**Критерий готовности:** 50 валидированных черновиков публикуются одним
нажатием, страница показывает `done/total/failed`, упавшие можно перезапустить,
и ни один SKU не получил второй POST.

### Этап B — многотоварный фид

Сейчас 200 листингов = 200 фидов. Walmart принимает массив, и продавцы так и
заливают тысячи.

- Собирать `MPItem[]` пачками (начать с 20, поднять после замеров).
- Разбирать **по-позиционный** результат из статуса фида
  (`itemDetails.itemIngestionStatus`), а не только общий статус фида.
- Забор «один SKU — один POST» переезжает на уровень позиции внутри фида:
  позиция входит в фид ровно один раз, и её attempt привязан к этому фиду.

**Осторожно:** пока по-позиционный разбор не написан и не проверен на живом
фиде, партионный фид опаснее одиночного — при частичном отказе непонятно, что
именно не встало. Поэтому этап B идёт **после** A, и переключение делается
флагом, с возможностью вернуться к одному товару на фид.

**Открытый вопрос, требующий живой проверки:** максимальное число позиций в
одном `MP_ITEM` фиде и лимиты частоты подачи. Не выдумывать — снять с API.

### Этап C — непрерывная фабрика

Крон, который каждый час строит N листингов. Ему нужно то, чего сегодня нет:
**очередь целей**.

- **Источник целей.** Сегодня цель = промпт → поиск по каталогу. Для нонстопа
  нужен список товаров-доноров, которые ещё не листингованы: дедупликация по
  каноническому варианту против уже существующих SKU, чтобы фабрика не делала
  один и тот же суп во второй раз.
- **Политика.** Категории, размеры упаковки, целевая маржа, канал — сохранённый
  профиль, а не промпт каждый раз.
- **Расписание.** `/api/cron/bundle-factory-schedule`, раз в час: взять из
  очереди N целей, создать сборку, отдать обычному тику.

**Обязательные предохранители** (без них нонстоп — это способ быстро сделать
много ошибок):

| Предохранитель | Зачем |
|---|---|
| Потолок в сутки и в неделю | Walmart отправляет аккаунт на ревью за резкий всплеск новых товаров |
| Потолок расходов провайдеров | Обогащение платное; фабрика не должна съесть бюджет за ночь |
| Стоп при доле ошибок выше порога | Систематическая поломка не должна размножиться на 500 листингов |
| Нижний порог пула UPC | 13 037 сейчас; при 10/час это ~54 дня |
| Стоп при просадке здоровья аккаунта | Модуль Account Health уже есть |
| Пауза одной кнопкой | Оператору нужен рубильник, а не правка крона |

### Этап D — проверка на масштабе

Тысячу листингов глазами не посмотреть. Значит, проверка должна быть выборочной
и исключенческой:

- автоматическая проверка витрины покупателя по каждому опубликованному SKU
  (уже есть) — на масштабе она становится главным контролёром;
- **очередь исключений**: оператору показываются только расхождения, а не всё
  подряд;
- случайная выборка на ручной просмотр (владелец говорит «проверю штук 10» —
  пусть система сама выбирает эти 10 случайно, а не первые попавшиеся).

---

## 5. Порядок и почему такой

1. **A. Партия в интерфейсе** — снимает главную боль (200 нажатий), ничего не
   ослабляет, переиспользует готовую механику очереди.
2. **D. Очередь исключений** — до того, как объёмы вырастут, иначе проверять
   будет нечем.
3. **C. Непрерывная фабрика с предохранителями** — когда партии публикуются
   надёжно.
4. **B. Многотоварный фид** — оптимизация скорости; нужна только когда объёмы
   реально упрутся в время, и требует живых замеров лимитов Walmart.

---

## 6. Что должен решить владелец

- **Потолок автопубликации.** «Сотни» — это сколько в сутки без отдельного
  разрешения? Публикация остаётся его решением (AGENTS.md §2); на масштабе это
  превращается в один заранее заданный потолок вместо решения по каждому SKU.
- **Что делает крон сам:** только строит черновики (публикация — ручная партия),
  или строит и публикует в пределах потолка.

## Этап A: состояние на 2026-08-03 (приостановлен на середине)

Работа прервана осознанно: владелец попросил сначала довести живую публикацию
одного листинга. Ниже — точка подхвата, чтобы не переизобретать.

### Решения владельца (2026-08-03)

- **Потолок автопубликации — 25 в сутки**, с последующим подъёмом до 100 и 250
  по мере того, как полоса докажет себя. Через studio-полосу на тот момент не
  было опубликовано ещё ни одного листинга.
- **Крон должен быть настраиваемым, а не «или/или»**: сколько строить, сколько
  публиковать, публиковать сразу или после ревью, и с какой периодичностью
  (раз в час / раз в 5 часов / раз в сутки). Это меняет Этап C: нужен профиль
  политики, а не зашитое поведение.

### Сделано и лежит в main

| Что | Где |
|---|---|
| Модели `PublishBatch` / `PublishBatchItem` | `prisma/schema.prisma` (добавлением в конец) |
| Миграция | `prisma/migrations/20260803190000_publish_batch_queue` |
| **Таблицы применены к Turso и проверены** | `scripts/turso-migrate-publish-batch-queue.mjs` |
| Общий модуль публикации одного черновика | `src/lib/bundle-factory/publish-one-draft.ts` |
| Движок очереди | `src/lib/bundle-factory/publish-queue.ts` |

Маршрут `drafts/[id]/publish` уже переведён на `publishOneDraft`, поэтому
одиночная кнопка и будущая очередь физически не могут разойтись.

### Что заложено в движок очереди

- Потолок считается по **скользящему окну 24 часа** и по факту записей в
  `MarketplaceSubmissionAttempt` — то есть учитывает и одиночные публикации,
  сделанные мимо партии. Календарные сутки дали бы всплеск 25 в 23:59 плюс 25 в
  00:01, а это ровно та форма, за которую Walmart отправляет аккаунт на ревью.
- Позиция помечается `posted` **до** того, как запись уходит, а не после.
  Пометка после — это догадка, выданная за протокол.
- Оборванная позиция, чей POST мог состояться, уходит в `UNKNOWN` и остаётся
  там: её судьба выясняется чтением, никогда повторной отправкой. Авторитет —
  строка в ledger, а не истёкшее время.
- Позиции сверх потолка **остаются в очереди**, а не отклоняются: это честное
  поведение для «опубликуй эти 200 по 25 в сутки», и вызывающая сторона получает
  число, чтобы оператор не гадал.

### Осталось

1. API постановки партии и чтения прогресса + крон-бэкстоп (по образцу
   `bundle-factory-tick`, который уже так работает для сборки).
2. UI: «Publish selected (N)» ставит партию в очередь вместо цикла в браузере;
   вкладку можно закрыть.
3. Этап C — настраиваемый профиль политики (см. решения владельца выше).

Порядок из плана не меняется: A, затем D (очередь исключений), затем C, затем B.

## Состояние этапов на 2026-08-06

### Этап B — многотоварный фид · ПОЛОВИНА

Ограничение подтверждено документально: **~10 фидов в час** (см.
`docs/marketplace-rules/walmart/kb/feeds-maintenance-and-errors.md`). Цель
владельца — 10 **листингов** в час, то есть один фид на листинг съедает всю
квоту на минимальной партии.

Хорошая новость: **по-позиционный разбор уже написан и работает.** Опросчик
находит свою строку в `itemDetails.itemIngestionStatus` по точному seller SKU,
значит двадцать листингов с одним feed ID каждый прочитает свой результат и свои
ошибки. Предостережение из первой редакции плана снято.

Сделано: `walmart-batch-feed.ts` — сборщик, который отказывается отправлять всё,
что можно проверить заранее: один и тот же SKU дважды, один и тот же product ID
дважды, разные версии спеки в одном фиде, payload не из ровно одной позиции,
SKU в payload, не совпадающий с заявленным. Восемь тестов.

Осталось: транспорт. Забрать N заборов, один POST, привязать один feed ID ко
всем N попыткам, при неизвестном исходе увести все N в `UNKNOWN` без повторов.
Это самый опасный код в системе, и его нужно проверять на живом фиде, а не на
моках — поэтому он отдельным шагом.

### Этап C — ограничители · ГОТОВО

`walmart-factory-rails.ts`. Расписание спрашивает три вещи, прежде чем что-либо
опубликовать:

| Ограничитель | Условие | Что делает |
|---|---|---|
| `PAUSED` | оператор нажал «Pause everything» | останавливает **всё**, включая партии, поставленные человеком |
| `ERROR_RATE` | ≥50 % отказов за 24 ч при выборке ≥5 | останавливает расписание: публиковать дальше то же самое — это заявка на проверку аккаунта |
| `UPC_POOL_FLOOR` | свободных номеров <50 | последние номера уходят выбранным листингам, а не расписанию |

Пауза — отдельная ручка от режима: остановка линии не должна забывать, работала
ли она сама. Правила чистые и покрыты семью тестами; читатель видит их без базы
перед глазами.

### Этап B — транспорт написан, живым фидом не проверен

`walmart-batch-submit.ts`: один POST на партию, все позаборные ограждения на
месте. Порядок внутри одной позиции: проверить номер в каталоге → собрать payload
тем же `submitToWalmart` в сухом прогоне с `validateLiveSpec` → взять забор.
Позиция, которую не удалось подготовить, **пропускается с причиной**, остальные
летят без неё.

Что сделано отдельно и намеренно:

- **Пометка `REQUESTING` для всех N до POST.** Если она упала на середине —
  ничего ещё не отправлено, партия целиком отступает. Листинг, помеченный
  «отправляем», за которым нет фида, остаётся неизвестным навсегда; это самое
  дорогое состояние в системе.
- **Одобрения перечитываются непосредственно перед сетью.** Отозванное за время
  подготовки останавливает весь фид, а не едет внутри него.
- **Фид шаблонов доставки тоже партионный** (`buildWalmartSkuTemplateMapBatch`) —
  иначе лимит, который считает фиды, а не позиции, не сдвинулся бы.
- **Неизвестный исход POST = `UNKNOWN` для всех N, без единого повтора.** Партия
  умножает цену этого состояния на двадцать — поэтому размер партии 20, а первая
  живая партия должна быть **на двух листингах**.

Чего нет: прогона на живом фиде. На момент записи не опубликован ровно один
Walmart-листинг (`UY`), и он неисправим по другой причине, — отправлять нечего.
Инструмент готов: `scripts/walmart-publish-batch.ts --ready --limit 2 --apply`.
Очередь публикации на партионный путь **не переключена**: одиночный путь доказан
семью живыми листингами, партионный — нет.

### Этап B — ДОКАЗАН живым фидом · 2026-08-08

Первая настоящая партия: **два смешанных листинга одним POST**.

```
MP_ITEM        18C9F79763255A26B81C3ABA7BD332E6@AXkBBgA
SKU_TEMPLATE   18C9F7978C3551FF8027F490AB856C80@AX0BBgA
AU-WMKW-CATL → walmart.com/ip/20799369088
DZ-WMVZ-UNEY → walmart.com/ip/20813350350
```

Через 74 минуты: `PROCESSED — received 2, ok 2, failed 0`. Партионный формат
разобран правильно, обе позиции заведены как отдельные товары. Дальше обычный
для этой ветки `PENDING_REVIEW` до подтверждения витрины покупателя.

**Живой прогон нашёл шесть дефектов, которых не увидели ни 2074 теста, ни три
независимых ревью.** Это главный вывод дня: ревью находит то, что выводится из
кода; живая отправка — то, что можно узнать только у Walmart и своей же базы.

1. Вес `6.412` фунта — нужна кратность 0.01 (унции делятся на 16 нецело).
2. **Наша собственная** проверка отвергала законные цены: `39.26 / 0.01` в
   двоичной арифметике даёт хвост. Мы блокировали сами себя, и не только на
   смесях. Лечится `multipleOfPrecision` у Ajv.
3. Повторный промоушен затирает печать одобрения, а переодобрение её не
   возвращает — листинг уходил в тупик навсегда.
4. `validator-recipe-content` требовал поле «вкус», которого у супов Campbell's
   нет: название и есть вкус. Теперь имя товара его заменяет.
5. Одобрение выполняется **только** при реальной публикации, поэтому подготовить
   партию сухим прогоном было невозможно. Инструмент печатает одобрение сам.
6. Раньше: транспорт повторял POST фида (см. третье ревью).

Каждый отказ до успеха был `NOTHING_TO_SEND`: ни одного лишнего POST, заборы
освобождались. Fail-closed отработал как задумано.

**Осталось до массового производства:** подтверждение витрины по обеим позициям;
партия из десяти; переключение очереди и крона с одиночного пути на партионный;
доноры, чью упаковку нельзя вырезать из фона (1 из 5).
