## 0. Где мы относительно цели

Цель владельца: фабрика, которая по свободному заданию строит сотни листингов,
даёт выборочно проверить и публикует партию одним нажатием, а дальше идёт по
расписанию неделями.

| Способность | Состояние |
|---|---|
| Свободный запрос → строгое ТЗ | Код есть, **не работает**: оба API-баланса пусты |
| Сборка N черновиков без присмотра | **Работает.** Тик каждые 5 минут, 3 попытки, перезапуск упавших |
| Промоушен → валидация → одобрение | **Работает** |
| Публикация одного листинга | **Работает.** 2 живых карточки — первые товары, созданные нами в каталоге Walmart |
| Публикация партии одним нажатием | **Наполовину.** Идёт последовательно из вкладки браузера |
| Очередь на сервере, крон, потолки | Движок и таблицы есть, **нет API, крона и UI** |
| Восстановление после отказа | **Дыра.** См. дефект 2 |
| Выборочная проверка на объёме | **Нет** |

Ближе всего мы к «партия по кнопке». Дальше всего — от «идёт само неделями».

## 1. Дефекты, блокирующие фабрику

### D1. Смена UPC не лечит коллизию — причина не в номере · КРИТИЧНО

`UY-WMX5-TKBA` отбился с `ERR_EXT_DATA_0101119`. Номер заменён
`756441906035` → `756441906097`, отправлен заново — **тот же код через 4 минуты**.
При этом соседние номера того же блока (`…073`, `…080`) создали два живых
листинга.

Значит правило «отбилось по UPC → крутим UPC» не восстанавливает листинг, а
сжигает номера: каждая попытка отправляет один UPC в карантин навсегда.

Сейчас в карантине **2 998 из 17 168 (17,5 %)**, все из одного импорта
«Speedy free pool». Причину я не установил; рабочих версий две — совпадение по
GTIN производителя внутри payload либо конфликт с нашей же живой карточкой того
же товара в другой фасовке. Разбирать надо по payload, а не перебором номеров.

**Почему это стоп для фабрики:** на каждую позицию нужен UPC. При 17,5 %
карантина и неработающем восстановлении часть партии будет молча застревать.

### D2. Застрявший листинг не имеет пути назад без скрипта · КРИТИЧНО

Кнопка публикации у `FAILED` есть — `PUBLISHABLE_LISTING_STATUSES` включает
`PENDING`, `FAILED`, `RETRYABLE`. Но у листинга с карантинным UPC нажатие
повторяет ровно тот же отказ: **в интерфейсе нет действия «заменить номер»**.
`rotateQuarantinedUpc` вызывается только из скрипта, которого до сегодня не было
в репозитории.

Автоматика тоже не помогает: `WALMART_POLLABLE_LISTING_STATUSES` — это
`SUBMITTED`, `PENDING_REVIEW`, `SUBMITTING`, `SUBMISSION_UNKNOWN`. `FAILED`
опросчик не берёт, и правильно — но никто другой его и не подбирает.

**Итог:** каждый отказ требует человека с терминалом. На двухстах листингах это
не работает.

### D3. Этап A не закончен · КРИТИЧНО для масштаба

Есть: `publish-queue.ts` (enqueue, tick, progress, cancel, list), таблицы
`PublishBatch`/`PublishBatchItem` на боевой базе, суточный потолок
(`walmart_publish_daily_cap`, по умолчанию 25).

Нет: **ни одного API-маршрута**, **крона**, **UI**, **ни одного теста** на ~600
строк движка.

Сегодняшняя «партия» — последовательные запросы из вкладки браузера. Закрыл
вкладку — публикация оборвалась на середине.

## 2. Дефекты корректности

### D4. Расхождение схемы: таблицы очереди не зарегистрированы

`PublishBatch` и `PublishBatchItem` **существуют на Turso**, но записи о
миграции `20260803190000_publish_batch_queue` в `_prisma_migrations` нет —
таблицы созданы мимо ledger-а. `prisma migrate deploy` на чистом окружении
разойдётся с боевым.

### D5. Нет защиты от дубля при публикации

`recipe_fingerprint` не даёт создать одинаковый **черновик**, но ничто не мешает
опубликовать два листинга на один канонический вариант с одной фасовкой. У
Walmart есть политика дубликатов, и на объёме это риск для аккаунта, а не
косметика.

### D6. Список черновиков обрезан 100 строками

`take: 100`, без фильтров и пагинации. «Выделить всё» физически не может
захватить больше сотни новейших. При партии в 200–1000 владелец не увидит свою
партию целиком — то есть заявленный сценарий не выполняется на своём же объёме.

### D7. Ноль тестов на очереди публикации

Самый ответственный новый код ветки (потолки, идемпотентность, тик) не покрыт
ничем.

## 3. Наблюдаемость

### D8. Ledger не знает, каким фидом ушла отправка

`MarketplaceSubmissionAttempt.marketplace_submission_id` остаётся `null`; ID
фида пишется в `ChannelSKU.submission_id`. Первое же чтение ledger-а показало
`feed undefined` по всем строкам — данные есть, но не там, где их ищут.

### D9. (исправлено сегодня) Диагностика врала про причину

Отрисованная панель состава при ненастроенном R2 давала «нет текста состава» —
для товара, у которого состав лежит в трёх местах.

### D10. (исправлено сегодня) Инструменты жили на одной машине

`_ledger.mjs`, `_feed_status.ts`, `_rotate_upc.ts`, `_publish_one.ts` не были в
гите. Со второй машины нельзя было даже посмотреть, чем кончилась отправка.

## 4. Что проверено и работает

- **Публикация сквозь всю цепочку.** Две живые карточки: `FN-WM30-XEHS`
  (20765921612), `BB-WMNY-SFUX` (20746951075).
- **Описание доходит до покупателя.** Чтение нашей же витрины провайдером:
  `general.description` — 1 706 символов нашего текста. Вопрос «почему не видно»
  закрыт: `shortDescription` рендерится не в «About this item» (там
  `keyFeatures`), а ниже отдельной секцией.
- **Опросчик работает сам** — `/api/cron/bundle-factory-poll-pending` каждые 5
  минут; в `LIVE` переводит только по доказательству с витрины покупателя.
- **Заборы одноразовости целы:** `idempotency_key` по (SKU, payload),
  `active_key` по SKU, перепроверка дрейфа перед POST,
  `SUBMISSION_UNKNOWN` не переотправляется никогда.
- **Остатки** 50 на все ship node при переходе в LIVE.
- **Цена** по правилу владельца (70 % ROI на товар с упаковкой).
- **Тайминг Walmart измерен:** подтверждение фида ~2 сек, создание нового товара
  63–83 мин, правка существующего ~1 мин.

## 5. Порядок устранения

1. **D2 + D1** — восстановление после отказа. Сначала кнопка «заменить UPC и
   отправить заново» в интерфейсе, затем настоящая причина коллизии. Без этого
   любой объём упрётся в ручной труд.
2. **D3** — API + крон-бэкстоп + UI очереди. Партия должна переживать закрытую
   вкладку.
3. **D7** — тесты на очередь, до того как ею начнут публиковать сотнями.
4. **D6** — фильтры и пагинация в списке.
5. **D5** — проверка дубля перед постановкой в очередь.
6. **D4** — привести ledger миграций в соответствие с боевой базой.
7. **D8** — писать feed id и в attempt.

Не в этом списке, но названо владельцу отдельно: интерпретатор свободных
запросов не работает, пока пусты оба API-баланса.
