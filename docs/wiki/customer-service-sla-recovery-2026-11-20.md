## Первопричина и исправление

Регрессия воспроизведена на реальных артефактах `worker/20261120T150000Z/thread-1.png`: визуально `Due: 10 hrs`, OCR верхней плашки — `Due: 10 brs`. Сам regex уже поддерживал `hrs`. Повторная проверка на `worker/20261120T151306Z/thread-1.png` показала `Due: 9 brs` в обеих OCR-областях.

Теперь признак SLA определяется по явным меткам Amazon `Over SLA` / `Due: N`. Единица времени не нужна для этого булева признака; из неё не рассчитывается deadline. Считываются плашка ветки и выбранная строка списка, противоречие оставляет SLA неизвестным. Исходные OCR-строки сохраняются в `thread-readings.json`.

| Дефект | Исправление | Проверка |
|---|---|---|
| Ошибка единицы `hrs → brs` роняла цикл | Разбор явной метки Due независимо от единицы; второй источник плашки | Оба реальных кадра (10 hrs и 9 hrs), тесты Due/Over SLA |
| Одна ветка уничтожала всю очередь | Изолированные ошибки `sla`/`identity`, сохранение прочитанных веток и независимых счётчиков | Реальный промежуточный partial-цикл сохранил 2 ветки; unit test плохой первой identity сохраняет вторую |
| Неполный SLA мог превратиться в неверную сумму | Aggregate Over SLA = null при любом непрочитанном SLA/identity | API validation и тесты |
| Частичный список выглядел полным | API `coverage`, `readStatus`, `errors`; UI предупреждение; digest явно сообщает о неполноте | TS + UI harness + Python digest test |
| Ошибки уведомлений скрывались | Убран `except: pass`; `notification.json` с sent/throttled_or_pending/unconfirmed; история попыток append-only; timeout CLI поднят с 40 до 120 с | Тест TimeoutError сохраняет unconfirmed; реальная доставка 1805 и 1807 |

Полный снимок сохраняет контракт API `state=fresh`, дополнительно `readStatus=ok`. Worker записывает `state=ok`. Частичный снимок остаётся свежим по времени, но получает `readStatus=partial`, явно неполное покрытие и null для неподтверждённых метрик. Снимок целиком не принимается при непроверенном аккаунте, нечитабельных общих счётчиках или потере транспорта.
