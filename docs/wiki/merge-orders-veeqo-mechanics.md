# Merge Orders — как это устроено у Veeqo (доказано на живых данных, 2026-07-31)

Разбор проведён против прод-API Veeqo и реальных заказов аккаунта. Всё ниже —
наблюдения, а не документация: Veeqo эти поля и параметры **не публикует**.

## Что такое merge

Покупатель делает два заказа подряд на один и тот же адрес. Veeqo позволяет
слить их в один отгрузочный заказ, купить одну этикетку вместо двух и разослать
её трек-номер обратно во все исходные заказы на площадках.

## Условия (по документации Veeqo и по факту)

- Одинаковый адрес доставки — Veeqo считает по нему собственную чек-сумму.
- **Одинаковая валюта** — прямое ограничение из хелпа Veeqo.
- Фильтр в их UI: `status=awaiting_fulfillment`, `mergeable=true`,
  `pick_status=unpicked`.
- **Только внутри одного канала.** В хелпе прямо не сказано, но подтверждено
  дважды: кейс-стади дизайнера фичи («странно купить в разных каналах и
  получить одну посылку») и все 16 наших реальных мержей — ни одного смешанного.
- Veeqo **не** ищет кандидатов сам: продавец должен зайти в фильтр и увидеть их.

## Поля заказа, которых нет в документации

| Поле | Что это |
|---|---|
| `mergable_checksum` | 64-символьный хеш адреса. **Пишется без второй «e»** — это опечатка в их API, не у нас. Совпадает у всех заказов одной группы. |
| `merged_to_id` | На исходном заказе — id объединённого. `null` = не объединён. |
| `merged_order` | `true` на самом объединённом заказе. |
| `mergeable_id` | Грубый ключ локальности, вида `US11697` / `US98550-4204` (страна + ZIP). |

**`GET /orders?mergeable=true` работает**, хотя не документирован. Проверено
контрольным опытом: базовый запрос → 5 заказов, `mergeable=true` → 0,
`mergeable=false` → 5, несуществующий параметр `zzz_not_a_real_param=true` → 5.
Несуществующий параметр игнорируется, а `mergeable` — нет, значит он honoured.

Эндпоинта на **сам мерж** в публичном API нет — только List / Create / View /
Update / Note / Cancel. Кнопка Merge в их UI ходит во внутренний API.

## Что происходит при объединении

Разобрано на реальном заказе `#P-1988529619` (28.07.2026):

**Объединённый заказ (родитель):**
- номер `#P-<id>`, канал `direct` / «Merged Orders»
- `merged_order: true`, `merged_to_id: null`
- позиции — **сумма** позиций исходных (1 + 1 = 2 × BZ-JGGO-ENJ6)
- сумма — **сумма** исходных (31.82 + 31.82 = 63.64 USD)
- своя аллокация и своя отгрузка

**Исходные заказы (дети):**
- сохраняют свой номер, канал и аллокацию
- `merged_to_id` = id родителя, статус → `shipped`
- **та же `mergable_checksum`, что у родителя**

## Как трек попадает обратно на площадки

Механизм подтверждён по таймстемпам с точностью до миллисекунд:

| Заказ | shipment | tracking | charges | создан |
|---|---|---|---|---|
| `#P-1988529619` (родитель) | 1417557985 | `1Z142CY90335515328` | BASE_RATE **$10.30** | 22:00:00.525 |
| `111-4675174-3270642` | 1417557997 | `1Z142CY90335515328` | `{}` | 22:00:01.029 |
| `111-1361395-7274601` | 1417558000 | `1Z142CY90335515328` | `{}` | 22:00:01.341 |

То есть: покупка этикетки идёт **только на родителе**, а Veeqo через полсекунды
создаёт на каждом исходном заказе **зеркальную отгрузку с нулевой стоимостью и
тем же трек-номером**. Именно эта зеркальная отгрузка и уезжает на Amazon и
Walmart. Деньги списываются один раз.

## Сколько это стоит и сколько теряется

За 06–29 июля 2026 в аккаунте: **16 объединений, 35 исходных заказов,
19 непокупленных этикеток**. Размеры групп: 14 групп по 2, одна по 3, одна по 4.
По каналам: Amazon 25, Walmart 10.

При этом чек-сумма находит **ещё 28 групп**, которые объединены не были. Это
верхняя оценка, а не 28 подтверждённых потерь: часть уже отгружена, часть
отменена, и не все были доступны к мержу одновременно. Но порядок понятен —
вручную ловится заметно меньше половины.

## Что из этого следует для нашего кода

Наш `deliverySignature()` вручную нормализовал адрес и нёс оговорку «если Veeqo
находит пары, которых не находим мы — подкрутить нормализацию». Это больше не
нужно: группируем по **их** чек-сумме, и совпадение с их списком получается по
построению, а не по подражанию.

Проверено на истории: **16 из 16** реально выполненных мержей воспроизводятся
правилом «одинаковая `mergable_checksum` + один канал», расхождений ноль.

Также добавлены исключения: заказ с `merged_to_id != null` и сам объединённый
заказ кандидатами больше не считаются — иначе оператору предлагалось бы слить
то, что уже отгружено.

## Исправление прежнего документа

[`merge-orders-design.md`](merge-orders-design.md) утверждал, что мы вынуждены
имитировать их сопоставление адресов. Это неверно: Veeqo отдаёт и чек-сумму, и
рабочий фильтр `mergeable=true`. Верным в том документе остаётся главное — на
**сам мерж** публичного эндпоинта нет.

## Замеченная аномалия

У родителя `1975021580` двумя детьми числятся заказы с **одинаковым номером**
`200015194860003`, но разными id Veeqo (1972736102 и 1972736098). Похоже на
дубль заказа Walmart внутри Veeqo. К мержу отношения не имеет, но стоит
проверить отдельно.
